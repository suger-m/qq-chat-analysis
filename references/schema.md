# 解密库结构参考（nt_msg.db 等）

写自定义 SQL 或排查数据问题时读这里。**日常分析不要直接写 SQL**——用 `cli.py`，
它已封装下面全部容错逻辑。

## 数据库一览

数据在 `<数据目录>/output/<账号ID>/` 下（数据目录由 QQ_DATA_DIR 指定）：

| 文件 | 内容 | 备注 |
|---|---|---|
| `nt_msg.db` | 消息主库（群/好友/临时会话等） | 列名 = protobuf 字段号，需双引号包裹 |
| `group_info.db` | 群资料与成员 | `group_list` 群名、`group_member3` 成员 |
| `group_msg_fts.db` | 群消息**明文**正文索引 | 有索引延迟（见下） |
| `buddy_msg_fts.db` / `msg_fts.db` | 好友消息明文 | 本次分析未用 |
| `emoji.db` | 经典表情 ID→名称 | `base_sys_emoji_table` |

## `group_msg_table` 关键列

| 列 | 含义 |
|---|---|
| `40001` | msgId（雪花号，1e18 级，**超出 JS 安全整数**，必须按字符串处理） |
| `40002` | 分片序号（与 40027/40003 组成唯一索引） |
| `40003` | msgSeq，**单调递增 ≈ 时间**（排序应该用这个） |
| `40011` / `40012` | msgType / subType |
| `40020` | 发送者 **NT UID**（`u_xxxx`），坏页少，推荐首选 |
| `40021` | 对端 ID = 群号（群消息） |
| `40027` | 本地会话 ID = 群号（**索引主键**） |
| `40033` | 发送者 **QQ 号**，**坏页极多**，批量读会大面积失败 |
| `40050` | Unix 时间戳（秒） |
| `40090` / `40093` | 群名片 / 昵称（快照，常为空） |
| `40800` | **protobuf 消息体**（元素列表，blind decode 后用 `45002` 分发） |
| `40900` | 引用快照 / `40801` 额外数据 |

### 索引

```
group_msg_table_idx40027_40003_40002   UNIQUE (40027, 40003, 40002)   ← 分页排序用它
group_msg_table_idx40027_40003         (40027, 40003)
group_msg_table_idx40011_40012_40027   (40011, 40012, 40027)
group_msg_table_idx40027_40058         (40027, 40058)
```

## 消息元素（`40800` 解码后）

`45101` 是一层包装，其 `45002` 是**元素列表**；每个元素自身也有 `45002` 表示**类型**：

| 45002 | 类型 | 主要字段 |
|---|---|---|
| 1 | 文本 | `45101` 文本；`45102=2` 表示带 @（`45105` 是被 @ 的 uid） |
| 2 | 图片 | `45402` 文件名、`45405` 字节数、`45411`/`45412` 宽高、`45802/45803/45804` 下载直链、`45816` CDN 域名、`45812` 本地缓存路径 |
| 3 | 文件 | `45402` 文件名、`45405` 字节数、`45503` fileid |
| 4 | 语音(ptt) | `45402` 文件名（SILK 格式）、`45405` 字节数 |
| 5 | 视频 | `45402` 文件名、缩略图字段 |
| 6 | 经典表情 | `47601` 表情 ID、`47602` 名称（如 `b'/\xe6\xb1\xaa\xe6\xb1\xaa'`） |
| 7 | 引用/回复 | 见下方专节 |
| 8 | 系统灰条 | 见下方专节（撤回 / 入群 / 戳一戳） |
| 10 | App / 小程序卡片 | **`47901` 是 JSON 字符串**（blind decode 得到 bytes） |
| 11 | 商城/超级表情 | `80810` ID、`80900` 名称、`80824`/`80903` hash |
| 14 | 机器人 Markdown | `48701`（前面有 `[](%7B"version":2%7D)` 前缀需剥掉） |
| 16 | XML 卡片 | `48602`（可能 gzip/zlib 压缩，wbits 15+32 兜底） |
| 17 | 按钮组 | `48751` → 行 → `48753` → 按钮（`48755` 文案、`48761` 跳转） |
| 21 | 语音通话提示 | `48153` / `48157` |

> ⚠️ **资源类元素（2/3/4/5）不要以「有没有文件名」来判定是否存在**：`45402`
> 偶尔会被 blind decode 解成嵌套结构（取不到文件名）。此时类型码本身 + `45405`
> 体积 + `45411/45412` 尺寸仍然可读，应当照常出 `[图片]` 之类的标记
> （`QQStore._res_item` 已处理）。否则整条消息会退化成「[非文本消息]」。

### `45002=7` 引用/回复（对话线索的关键）

| 字段 | 含义 | 备注 |
|---|---|---|
| `47413` | 被引用的**正文全文** | 完整保留，不截断；但引用的是图片时可能塞的是**本地缓存路径**，需要清洗 |
| `47403` | **原消息发送者 QQ 号**（int） | 最可靠的署名来源，可回群成员表换昵称 |
| `47404` | 原消息时间戳（**秒**） | 用于渲染「回复 10-03 17:19 昵称」 |
| `47421` | 原发送者**全局 QQ 昵称** | ⚠ 不是群名片，**不能直接当署名用**，见下方 |
| `47401` | 原消息 seq | 仅部分消息带 |
| `47423` | 被引用的**原始元素** | 图片引用时文本在 `47423.45101`（如 `[图片]`），类型在 `47423.45002` |

实测覆盖率：**42/42 条引用都能还原出署名**（42 条中 39 条带 QQ号），只给正文会
丢掉「这条在接谁的话」这层信息。

#### ⚠ `47421` 是全局昵称，署名必须回本群名片

`47421` 存的是**账号级 QQ 昵称**，而正文行首用的是**本群群名片**。群名片改过名的
人就会出现两个名字。实测本群 34 条引用里 **6 条错**：`青衫` 被写成 `竹里`（×4）、
`夜航` 被写成 `Ye?`（×2）—— 读起来像两个人在对话。

所以渲染引用行时**必须**用 `47403`（原发送者 QQ号）回本群名片解析（走
`qanalysis.display_name(..., gmap)`），只有 `47403` 缺失时才退回 `47421`。
`47403` 也有约 7% 的引用不带（实测 42 条中 3 条），这时 `47421` 仍然比没有强。

配套：**只被引用、窗口内没发言**的人也要进成员对照表（计数 0），否则 Agent
拿不到他的 QQ号、配不上头像（实测某群 32 条引用里有 1 人是这种情况）。
`tests/regress.sh` 的 `quote_author` 断言就是在守这条：引用行的署名必须能在
成员表里找到。

### `45002=8` 系统灰条

灰条**不是一段纯文本**，而是一套带子类型的结构体（`45003` = 子类型）。
`_gray_tip_text()` 负责还原，优先级：XML 模板 → JSON 模板 → 子类型专用解析 → 中性描述。

| `45003` | 形态 | 字段与还原方式 |
|---|---|---|
| 1 | **撤回** | `47705` 操作者名、`47714` 原发送者名、`47713` 附言(wording)、`47710` 被撤回的原始元素 → `X 撤回了一条消息（且有错别字）` |
| 4 | 群成员变动 | `48501` 子码、`48503`/`48504`（uid/名）、`48506`/`48507`、`48541→48521→{1000:uid, 20002:名}`；**语义未确证**，只输出 `[系统消息: A、B]` |
| 12 | 邀请入群 | `48214` 是 `<gtip>` XML（占位符已由 `48210`/`48217` 填好）→ `A邀请B加入了群聊，并附带了30条聊天记录。` |
| 17 | 通用灰条 | `48214` XML 或 `48271` JSON → 戳一戳 / 入群提示等 |
| 0/其他 | JSON items | `48271` = `{"items":[{"type":"qq","uid":…,"nm":…},{"type":"nor","txt":…}]}` |

**`<gtip>` XML 是 token 流，不能「去标签」**：

```xml
<gtip align="center">
  <qq uin="u_xxx" col="3" jp="<示例ID_15>"/><nor txt="邀请"/>
  <qq uin="u_yyy" col="3" jp="<示例ID_16>"/> <nor txt="加入了群聊，并附带了30条聊天记录。"/>
</gtip>
```

逐 token 还原（`<qq>`→人名：`nm` 属性 → `uin` 反查昵称 → `jp`(QQ号)；`<nor>`/`<url>`→`txt`），
token 之间**不加分隔符**。直接删标签会丢掉 `<nor>` 的正文（得 `邀请 加入了群聊…`），
更糟的是 blind-decode 会把兄弟字段 `48210` 的昵称和 `48217` 的占位符
（`invitor`/`invitee`/`msg_num`）当成正文捞出来（得 `w21 瑜笙 invitor invitee msg_num 30`）。
所以 `text_from_blob()` 命中灰条时**必须优先走模板解析**，不再跑通用遍历。

**不解码识别灰条**：元素 `45002` 恒为 `8`，但承载文案的字段并不统一 ——
戳一戳 / 入群走 `48214` / `48271`，而**撤回两个模板字段都没有**（走 `477xx`）。
所以判断「是不是系统消息」必须匹配协议标记本身（`45002=8` 的 tag 字节
`_EL_TYPE_TAG + b"\x08"`）；只匹配 `48214`/`48271` 会漏掉整批撤回（实测漏 ~40%）。
`is_gray_blob()` 即做此事：纯字节查找、不解码，也不会把用户自己发的
「撤回了什么瓜」这类文本误判成系统消息。导出的 `kind` 据此标成 `system`，
`read_group()` / `collect()` 返回的消息也带 `system: true/false`。

**灰条的 `40033`（发送者）实测情况**（本群 122 条灰条逐条核对）：

| 灰条类型 | 发送者字段 | 与文案的关系 |
|---|---|---|
| 撤回 | **有**，且就是撤回者本人 | 59/61 的 `40033` 昵称出现在文案里 |
| 戳一戳 / 拍一拍 | **没有**（空 / `0`） | 操作人只出现在文案里（`A戳了戳B`） |
| 入群 / 邀请 | 多为空 | 只能从文案里的 `48210` 昵称还原 |

所以**不是「归错人」**，真正要处理的是两件事：

1. **渲染歧义**：`display_name` 取**本群群名片**，而灰条文案里嵌的是**全局昵称**
   —— 同一个人显示成两个名字。`曲率: 折耳根 撤回了一条消息` 读起来像 曲率
   在转述别人的事，其实是同一人（`<示例ID_9>` 的群名片是 `曲率`、全局昵称是
   `折耳根`）。渲染层对 `system=True` 的行统一署「系统」，比猜名字更准。
2. **统计口径**：灰条是事件通知而非一次发言，混入会虚增发言量（本群占 3.3%），
   且无发送者的那批会聚成一个幽灵成员「未知」（实测 142 条全落进一个空 uin 桶）。
   统计层统一走 `speakers()` 过滤 —— `user_profiles` / `night_owls` /
   `emoji_rank` / `image_rank` / `quote_network` / `lurkers` 都已接入。

分析层（Agent）也不要把灰条当引用或议题发言，见 `analysis-guide.md` §0②。

## 成员映射（`group_info.db`）

```sql
-- 群名
SELECT "60001","60007" FROM group_list;                     -- 群号, 群名
-- 群成员: uid / QQ号 / 昵称 / 群名片
SELECT "1000","1002","20002","64003"
FROM group_member3 WHERE "60001"=?;                          -- 按群过滤
```

- `1000` = NT UID、`1002` = QQ 号、`20002` = 昵称、`64003` = **群名片**
- 群名片是**分群**的：同一个人在不同群名字不同，单群分析要优先用本群名片
- `nt_msg.nt_uid_mapping_table`（`48902`→`1002`）只覆盖约 6 千条，**不能作为主映射**

## 已知异常与容错（重要）

1. **rowid 与时间不同序**
   QQ 回填的历史行 rowid（≈7.766e18）比正常收发的行（≈7.692e18）**更大**。
   `ORDER BY rowid DESC LIMIT n` 会漏掉当天最新消息（实测 60 条错 58 条）。
   → 必须用索引：`WHERE "40027"=? ORDER BY "40003" DESC`。

2. **零星坏页**
   `GROUP BY`、`ORDER BY 非索引列`、跨页大范围扫描会抛
   `database disk image is malformed`。
   → 用 rowid 导航分批读；整批失败就降级逐行；坏行跳过。

3. **非 UTF-8 文本列**
   `group_member3.64003` 等列存有非法 UTF-8 字节。默认 `text_factory` 会
   **抛异常并中断整个游标遍历**（实测在 42215/102079 行静默截断，之后成员全部丢昵称）。
   → 连接时设 `text_factory = lambda b: b.decode('utf-8','replace')`。

4. **`40033` 坏页极多**
   批量 `IN` 读它大面积失败，逐行回退会把 8 万条放大成十几万次查询。
   → 只读 `40020`（UID），再用成员映射换 QQ 号（覆盖率可达 100%）。

5. **FTS 索引延迟**
   QQ 的 `group_msg_fts` 落后于最新消息，刚收到/刚发出的消息往往搜不到。
   → 正文优先取 FTS（快），缺失的从 `40800` 盲解析兜底。

6. **WAL**
   主库是 WAL 模式，解密脚本只处理 `nt_msg.db`，不管 `-wal`。QQ 运行时新消息可能
   只在 WAL 里（主库还没 checkpoint）。
   → 技能已把 `-wal` 的 mtime 一并计入新鲜度判断（`qqlib.freshness`），产物落后就
   自动重新解密（`cli.py fresh`），不必手动退出 QQ。见 SKILL.md「第零步」。

7. **空壳行**
   少量行 `40800` 为 NULL（QQ 未把内容同步到本地），与 WAL 无关，属于真·无内容。

## 本地媒体缓存（`<QQ 数据目录>\<QQ号>\nt_qq\nt_data\`）

| 类型 | 路径规则 |
|---|---|
| 图片 | `Pic/<YYYY-MM>/Ori/`（原图）、`Thumb/`（含 `_0` / `_198` / `_720` 变体） |
| 视频 | `Video/` |
| 语音 | `Ptt/`（SILK，需转换才能播放） |
| 经典表情 | `Emoji/BaseEmojiSyastems/EmojiSystermResource/<ID>/{png,apng}/<ID>.png`（305/306 命中） |
| 商城表情 | `Emoji/marketface/<ID>/<md5>_aio.png`（本地缺图时可回落 CDN） |

商城表情 CDN（本地无缓存时）：
`https://i.gtimg.cn/club/item/parcel/item/<md5[:2]>/<md5>/300x300.png`
其中 `md5` = 元素 `80903` 字段 16 字节的 hex。

清晰度优先顺序：原图 > `_720` > `_198` > `_0`。
