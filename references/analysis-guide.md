# 分析框架与写作指南

这份文档解决一个问题：**拿到 `cli.py context` 输出的原料后，怎么把它变成一份
有价值的 `analysis.json`**。

核心原则：**报告的价值来自「读懂了内容」，不来自「数得清楚」。** 一份好的群聊
分析，应该让没在群里的人看完就知道：这段时间发生了什么、谁在推动话题、有什么结论
和后续。如果一份报告只是把词频和发言量换了个好看的外壳，那它没有价值。

---

## 0. 三条硬规则（先看这个）

### ① 标注人物一律用 QQ号，不要只写昵称

`context` 输出的**开头有一张「发言成员对照表」**，多列对齐，形如：

```
# ⚠ 以下昵称重名, 必须用 QQ号区分: 阿星=<示例ID_1>/<示例ID_2> | Kevin=<示例ID_3>/<示例ID_4>/<示例ID_5>
# 阿星⚠=<示例ID_2>      青衫=<示例ID_6>      夜航=<示例ID_7>      Momo=<示例ID_8>
# 曲率=<示例ID_9>     半夏=<示例ID_10>     云岫=<示例ID_11>       老周=<示例ID_12>
```

写 JSON 时把对应 QQ号填进 `uin` 字段（问答用 `asker_uin` / `answerer_uin`）：

```jsonc
{"name": "阿星", "uin": "<示例ID_2>", ...}                     // people
{"who": "阿星", "uin": "<示例ID_2>", "text": "..."}            // quotes
{"q": "虚拟线程怎么选", "asker": "麦冬", "asker_uin": "<示例ID_13>", ...}
{"title": "...", "contributors": ["<示例ID_2>", "<示例ID_9>"]} // topics
```

**为什么必须做**：报告会根据 QQ号去拉真实头像。只写昵称时程序要反查群成员表，
而**昵称重名在大群里是常态** —— 实测一个 千余人的群里有 7 组重名，短中文昵称
和常见英文名最容易中招。只写名字会把 A 的话记到 B 头上。填入准确 ID 可以避免同名误配；头像接口失败时仍需降级。

**带 `⚠` 的昵称必须查清是谁再填。** 不用猜 —— 用 `search` 或直接在原料里看
上下文（引用行里有 `└ 回复 … 昵称: 「…」`），确认后再填。

对照表里找不到的人（比如只在上下文里被 @ 提到、但没发言），就只写昵称，
程序会自动降级成首字头像，**不要编造 QQ号**。

> 懒得逐条核对时：先照写昵称，跑一遍
> `cli.py validate analysis.json --context ctx.txt`。**唯一命中**的昵称它会自动
> 补上 QQ号，**重名的**会明确报出来让你回去手工确认。比你自己反查可靠。

### ② 灰条不是发言，不许当引用

原料里以 **`系统:`** 开头的行是灰条消息：`X 撤回了一条消息`、`A戳了戳B`、
`A邀请B加入了群聊`、`X拍了拍Y的头`。

- **不要**把它们当某个人的发言写进 `quotes` / `qa` / `todos` / 议题 `points`
  —— 它是**事件通知**，不是「某人说的一句话」；
- 不要用它们做「活跃度 / 发言量」的判断依据（程序侧 `people` / `heatmap` 已经
  排除了灰条，你写 `insights` 时口径要一致）；
- 灰条文案里出现的名字**不一定**是「谁干的」：`A戳了戳B` 里 A 是发起人、
  B 是被戳的人，而撤回一般是「谁撤回的」在句首。别把被戳的人当成发言者。

如果**撤回/连戳这件事本身**值得写（比如某次集体撤回成了梗），写进 `insights` 或
议题的 `summary`，用中性叙述，别伪装成一条引用。

### ③ 只输出纯 JSON

- 用英文双引号 `"`，不要用中文引号 `“”`
- 内容里的引号转义成 `\"`
- **不要**用 ``` 代码块包裹，不要写任何解释性文字
- 字符串里避免换行，用普通文字表达

写入本地工作文件时使用 UTF-8；不要把真实身份字段放入帮助示例或用户答复。

**写完跑一遍自检**（`validate`）再渲染：它能抓出拼错的字段名、超 100% 的占比、
被转述的「金句」、署错人的引用。详见 SKILL.md「第三步」。

## 1. 聊天构成（quality）—— 报告的第一块，也是唯一的图表

**这是「结构」，不是「统计」。** 把整段时间的聊天内容划分成 3–6 个
**高层级、抽象、泛化**的维度，给出大致占比，每个维度配一句点评。

```jsonc
"quality": {
  "title": "群聊构成锐评",
  "subtitle": "近 5 小时 · 320 条",
  "dimensions": [
    {"name": "技术方案研究", "percentage": 38,
     "comment": "从 JDK 升级到虚拟线程，正经讨论占了大头，而且真的给出路线判断。"},
    {"name": "校招与就业焦虑", "percentage": 27,
     "comment": "简历筛选、手撕代码的套路，聊得最投入的一段。"},
    {"name": "无意义水群", "percentage": 20,
     "comment": "复读、拍一拍、表情包三件套，队形整齐。"}
  ],
  "summary": "这是一个「正经讨论和接梗交替推进」的群：一段硬核讨论后必然用复读收尾。"
}
```

**维度名必须抽象**：2–6 个字，**严禁**在 `name` 里出现具体人名、项目名、
报错内容或细碎事件（❌「大家在聊转正名额」✅「校招与就业焦虑」）。
具体的事件、吐槽、细节全部放进 `comment`。

占比是**大致估算**，总和 ≤ 100% 即可，不必精确到个位。

`summary` 写一句**全群表现**的总结，要具体、有画面感，不要「大家交流活跃」。

## 2. 议题（topics）—— 报告主体

### 什么算一个议题

判断标准三连：**有人抛话题 → 有人接 → 有信息增量**。

| 是议题 | 不是议题 |
|---|---|
| 有人问 JDK 27 有什么新特性，另一人给出 scoped value / AOT 的考据，第三人补充自家公司的升级现状 | 大家连续刷了 9 条同一句话（→ 这是群体现象，写进 `insights`） |
| 有人问「开源网关支持多少并发」，被用排队论认真回答 | 有人在群里发自拍（→ 除非引发了持续讨论，否则不进报告） |
| 一场跨越两天的压缩算法优劣讨论 | 三个人的日常寒暄 |

**反例**：不要按关键词切议题。同一个词（比如「Java」）可能在两天里出现在完全
无关的两段讨论中；也不要按时间硬切，一段 128 条的消息里可能有两个议题。

### 粒度

一份日报 3–6 个议题，周报 5–8 个。**按重要性排**，不一定按时间排。

- `heat` 用 1–5：5 = 全群卷入 / 持续一小时以上；4 = 多人参与、有结论；
  3 = 小众但完整；1–2 = 值得一提的边角。
- 跨天延续的讨论**合并成一条**，在 `summary` 里注明「隔天补完」。
- 纯刷屏、接龙、复读**不单独成题**。

### 一条议题必须有什么

```jsonc
{
  "title": "大厂校招的面试真相：手撕、简历流转与黑箱",
  "heat": 5,
  "tags": ["求职", "面试", "内幕"],
  "contributors": ["<示例ID_13>", "<示例ID_2>", "<示例ID_9>"],
  "summary": "从「面试看不看学历」开始，群里的在职者掏出了大量一线细节，讨论落点从「怎么进」转向「这套流程本身有多不透明」。",
  "points": [
    "手撕环节存在真实的「换题」操作，难度方差极大——同一轮面试有人被出基础题，有人被连出三道难题",
    "简历流转是这套流程里最受诟病的一环：候选人简历被某个部门先锁，其他部门就约不到面试，且候选人往往事前不知情"
  ],
  "quotes": [
    {"who": "夜航", "uin": "<示例ID_7>", "time": "17:08",
     "text": "这题都写不出来，建议回去等通知"}
  ]
}
```

- **`title` 要具体**。带上讨论的**张力**，读者才有兴趣往下看。
- **`contributors`** 是议题参与者（最多 5 人），按参与度排序，填 QQ号。
  报告会渲染成头像堆叠。
- **`summary` 讲因果**：谁抛的、怎么发展的、结论是什么。2–3 句。
- **`points` 是信息增量**，不是流程复述。写「虚拟线程适合 IO 密集，量不大就
  别折腾」，不要写「大家讨论了虚拟线程」。
- **`quotes` 必须原文**，不要转述、不要润色。1–3 条。

## 3. 问答（qa）—— 技术群最有价值的部分

只收**真正答上了**的。判断标准：提问者的问题被解决或被明确回应。

```jsonc
{"q": "虚拟线程怎么选？", "asker": "麦冬", "asker_uin": "<示例ID_13>",
 "time": "13:57",
 "answer": "IO 密集用虚拟线程，CPU 密集还是池；量不大就别折腾。",
 "answerer": "Momo", "answerer_uin": "<示例ID_8>", "time_a": "14:00"}
```

- 答非所问、纯玩笑式的回答**不要收**（如果有趣就进 `quotes`，不要进 `qa`）。
- 多人共同回答的，`answerer` 可以写「A + B」，`answerer_uin` 填主要那个人的。
- 冷知识：**提问响应速度**本身常常是最有价值的洞察（「这类问题平均 1 分钟内
  有准确回答」），读完原料后写进 `insights`。

---

## 4. 待办 / 决策（todos）

群里承诺过、且**尚未完成**的事。「我要做个视频」「下周面试」「代码还没发给你」
都算。`owner` 写谁承诺的，`note` 写时间点或状态。

不要收录「大家应该多喝水」这种没有人认领的口号。

---

## 5. 人物（people）—— 按角色，不按发言量

**这是最容易写坏的一块。** 发言人排行是统计数据，不是人物画像。

角色用**描述性词**，参考词库（可以自创）：

> 核心输出者 / 硬核科普位 / 玩梗主力 / 话题发起人 / 观察者 / 提问者 /
> 链接分享者 / 群宠 / 技术裁判 / 深夜常驻 / 新人

写法对比：

| ❌ 差 | ✅ 好 |
|---|---|
| 姓名：阿星；发言 128 条，全群第 2 | 角色：玩梗主力。发言量极高，擅长把任何话题变成梗，既是话题跳板、白嫖资源的实践者，也是复读队形的发起者之一 |
| 姓名：老周；发言 96 条 | 角色：硬核科普位。每当话题跑到底层细节他就开始认真，能把报错和线程模型串成一条线讲，并且真的会写程序交付 |

`desc` 必须来自**实际读到的行为**，不是猜测。`stat` 放客观描述
（「主导升级方案与压测两条主线」）或真实数字。

3–8 人。**宁可少写，不要凑数** —— 一个只说了三句话的人不该进人物榜。

---

## 6. 金句（quotes）

标准：**好笑、有观点、能独立传播**。宁缺毋滥，4–6 条。

```jsonc
{"who": "老周", "uin": "<示例ID_12>", "time": "16:53",
 "text": "这不是玄学，是你构造器没写",
 "note": "排查半小时报错后的收尾一句"}
```

`note` 交代**为什么值得摘**（语境、笑点、回应对象），这是金句从「一句截图」变成
「一个故事」的关键。

---

## 7. 洞察（insights）—— 只有读过内容才写得出来

这一块最能区分好坏报告。写法对比：

| ❌ 统计式（没读内容也写得出来） | ✅ 内容式（必须读过才写得出来） |
|---|---|
| 大家发言很活跃 | 这个群的提问—回答链路非常短，「线程怎么选」这类问题 1 分钟内就得到准确回答并附带延伸解释 |
| 技术氛围浓厚 | 技术讨论和玩梗并非互相打断，而是交替推进：一段严肃讨论后用复读收尾，再用一句玩笑把话题引向新的技术点 |
| 复读现象普遍 | 复读是这里最主要的社交货币。一条感叹被 9 人齐刷，说明群体认同靠「接住同一句话」完成，而不是靠点赞 |
| 每天讨论的话题很多 | 21 个话题段中超过一半在 10 分钟内结束，只有两条主线持续超过一小时 |

好的洞察通常是关于**这个群特有的东西**：讨论节奏、梗的运作方式、话题生命周期、
谁在维持秩序、信息如何流转。

3–6 条。

---

## 8. 风险（risks）

值得提醒的：账号安全（代理/封号）、隐私泄露（截图带内网信息）、合规、以及
**对外传播风险**。

```jsonc
{"level": "warn", "text": "多人讨论账号风控的规避手段，并有成员分享相关链接。"},
{"level": "info", "text": "群内玩笑尺度较大，部分内容不适合对外转发，交付时建议自行取舍。"}
```

`level` 取 `info`（提示）/ `warn`（注意）/ `bad`（严重）。

**处理敏感内容的原则**：群里出现擦边、攻击性或私人信息时，用**中性措辞概括成
社交现象**，不要展开细节、不要复述不当内容、不要点名。报告可能被转发，写的时候
要考虑当事人的感受。

---

## 9. 时间线（timeline）与附录（appendix）

- **时间线**：6–10 条，只标**真正改变了话题走向**的节点，不是消息日志。
  ```jsonc
  {"time": "10-01 13:15", "title": "一条线上事故复盘 → 两小时长谈",
   "desc": "从故障时间线一路聊到各家的发布流程。"}
  ```
- **附录**：3–6 条最有代表性的原文，让读者能核对。选那种「一句话就能说明当时
  在聊什么」的消息。

---

## 10. 反模式清单（写完自查）

先把这份清单当 checklist 过一遍，再跑 `cli.py validate` 做机器校验（见 SKILL.md
「第三步」）。人查语义，机查结构，两者不能互相替代。

- [ ] **人物是不是只写了昵称、没填 QQ号？** → 从成员对照表补 `uin`。
- [ ] **带 `⚠` 的重名昵称有没有先查清是谁？** → 查原料确认后填具体 QQ号。
- [ ] **有没有引用 `系统:` 灰条当发言？** → 删掉或改成中性叙述写进 `insights`。
- [ ] 有没有把发言排行 / 词频榜当成分析结论？→ 删掉，那不是分析。
- [ ] `quality` 的维度名是不是塞进了具体事件？→ 抽象成 2–6 字的维度。
- [ ] `title` 是不是太笼统（「技术讨论」「日常闲聊」）？→ 改具体。
- [ ] `points` 是不是在复述流程（「大家讨论了 X」）？→ 改成信息增量。
- [ ] `people` 是不是按发言量排的前几名？→ 按角色重写。
- [ ] `insights` 有没有统计式结论（「发言很活跃」）？→ 换成内容式观察。
- [ ] `quotes` 有没有转述而不是原文？→ 换回原文逐字摘抄。
- [ ] 有没有原料里没有、自己脑补的信息？→ 删掉。
- [ ] 敏感内容有没有展开细节？→ 改成中性概括。
- [ ] 输出是不是纯 JSON、英文引号、没有 markdown 包裹？

## 附一：原料格式速查

`cli.py context` 输出的开头是**成员对照表**（含重名提示行），之后是分段对话：

```
# 发言成员对照表 (昵称=QQ号)
# 写分析 JSON 时, 人物/问答/金句里请带上对应的 QQ号…
# ⚠ 以下昵称重名, 必须用 QQ号区分: 阿星=<示例ID_1>/<示例ID_2> | Kevin=...
# 阿星⚠=<示例ID_2>      青衫=<示例ID_6>      夜航=<示例ID_7>
# 曲率=<示例ID_9>     半夏=<示例ID_10>     云岫=<示例ID_11>

# 示例技术交流群 (<示例ID_14>)
2026-10-02 16:26 → 2026-10-03 22:35 · 500 条消息 · 40 人发言 · 13 个话题段
每小时消息量: 16时 124 · 17时 263 · 18时 26 · 23时 30
（原始聊天记录, 已按话题间隙 30 分钟分段, 时间正序）

## 段1 · 10-03 16:05–16:53 · 43 条 · 约 48 分钟
16:05 阿星: 明天有人去线下面基吗
16:07 曲率: 划水使我快乐 [图片]              ← 带媒体标记
16:32 系统: 折耳根 撤回了一条消息            ← 灰条是事件通知, 不是发言
16:53 老周: 就是构造器没写才会炸…
      └ 回复 10-02 16:35 云岫: 「为什么发完就撤回」   ← 引用行
```

- `#` 开头的整块是**元信息**（成员表与重名提示），不是聊天记录；消息行才有
  `HH:MM 谁:` 前缀。
- 时间在段内是 `HH:MM`；段跨天时自动变成 `MM-DD HH:MM`。
- 媒体标记：`[图片]` `[图片×3]`（同类合并）`[视频]` `[语音]` `[文件: x.zip 1.2MB]`
  `[图片 802×958]`（带尺寸）`[表情: 摸鱼]` `[表情包: 摸鱼]` `[QQ小程序: 标题]`
  `[分享]` `[图文卡片: 首行]` `[按钮: A / B]`。
- `系统:` 开头的是灰条消息（撤回、拍一拍、戳一戳、入群、邀请），**是事件
  通知而不是某人说的话**，不要当发言引用。文案里的人名也不一定是发言者
  （`A戳了戳B` 里 B 是被戳的人）。
- 命令结束时会打印 `原料 N 字符 · 约 M token`；接近 `--max-chars` 上限时会告警，
  说明最早的段已被丢弃 —— 这时缩小时间窗分批取，别在残缺原料上下结论。

## 附二：辅助统计命令的口径

需要给报告补充客观数字时才用这些（**不要**拿它们当分析结论）：

- **热词**：jieba 分词（缺 jieba 时降级 bigram）+ 停用词过滤，`[图片]`/`[表情]`
  等标签不计入；同一条消息内重复词只计一次。
- **复读/队形**：连续 ≥3 条**归一化后**（去空白/表情标签/链接、转小写）完全相同
  的消息。
- **潜水**：以群成员表为准；「零发言」是**相对分析窗口**的（`--days 30` 表示近
  30 天没说话，不是从没说过话）—— 回答时必须带上窗口。
- **夜猫子**：默认 0–6 点，按该时段发言量排序。
- **响应时间**：没有内置统计，需要人工从原料里估算（读 `qa` 的提问与回答时间）。
